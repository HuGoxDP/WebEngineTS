# Host → scenario parameters: not for benchmarking

**Status:** rejected for the reason it was proposed. Open as a general feature.
**Recorded:** 2026-08-19.

## The proposal

`IScenarioContext` (`src/engine/core/scenario/ScenarioTypes.ts`) gives scenario code three
things: `manifest`, `assets` and `importScript`. There is no way for the host that loads a
scenario to pass it a value. The suggested addition was a parameter channel:

```ts
Application.loadScenarioFromUrl(url, { params: { objectCount: 5000 } });
// surfaced to scenario code as:
this.context.params.objectCount;
```

## Why it was proposed

The benchmark suite needs one scene at four object counts. With no parameter channel, that is
four separate `.zip` archives that differ in one integer.

## Why that reason is rejected

**It puts a benchmark knob inside content.** The engine has a single-profiling-system policy
(`CLAUDE.md`, Key Technical Decisions): the measurement primitives — `MemoryProfiler`,
`Profiler`, `Benchmark` — are engine API, and the harness that drives them lives outside the
engine, in `WebEngineTS-Benchmarks`. It drives the optimizations from the outside, through URL
parameters, and measures from the outside. Scenario content is explicitly not allowed to embed
a harness or optimization toggles. A `params` channel introduced to carry `objectCount` is that
same thing arriving through a different door.

**It would stop the archives being what the platform ships.** The value of measuring
`Benchscene2` and `Benchscene3` is that they are real ScenarioCreator archives, run through
`Application.loadScenarioFromUrl` exactly as `testv/virtual-lab` runs them. A scene that only
produces its measured shape when the harness passes it a parameter is no longer the artefact
students receive, and the numbers stop describing the shipped path.

**Four archives is the honest cost.** They are generated by the same source with one constant
changed. That is duplication in the build output, not in the design, and it keeps each measured
artefact self-describing — the archive *is* the configuration, which is also what makes a run
reproducible from the archive alone.

## What is not rejected

A parameter channel as a **platform feature** is a legitimate design question: a scenario taking
a difficulty level, an interface language, a starting chapter, a student's saved progress. That
has real users and real requirements — persistence, validation, defaults when a parameter is
absent, versioning against the manifest, and a decision about whether the editor authors the
parameter schema.

If it is built, it should be designed for those requirements and justified by them. It should
not be justified by the benchmark use case, and the benchmark should not become its first
consumer by default.
