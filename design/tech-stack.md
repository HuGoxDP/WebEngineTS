# Технологический стек: что используется в проде и почему

Снимок сделан **2026-09-13** по реальным `package.json`, `rollup.config.mjs`, `tsconfig.json`,
`docker-compose.yml`, `Dockerfile.*` и `nginx/*.conf` всех пяти репозиториев экосистемы.
Версии — те, что стоят сейчас, а не «рекомендуемые». Если цифра здесь расходится с
`package.json`, прав `package.json`, а этот файл устарел.

Документ отвечает на три вопроса по каждому пункту: **что стоит**, **почему именно это**,
**чем оно лучше очевидной альтернативы** — включая случаи, где выбор имеет измеренную цену.

## 2. Почему именно так — по критическим решениям

### 2.1 TypeScript в `strict`, а не JavaScript

Главное архитектурное правило проекта — **Three.js не имеет права появиться в публичной
подписи**. Это правило исполнимо только там, где подписи существуют как проверяемый
артефакт. На JS оно превратилось бы в соглашение, которое нарушается в первый же занятой
день.

Второй аргумент — потребителей четыре, и все они получают движок как бинарный `.tgz`.
Единственное, по чему автор сценария понимает API, — это `WebEngineTS.d.ts`. Типы здесь
не удобство для разработчика движка, а **интерфейс поставки**.

Чем лучше альтернатив: JSDoc-типы дают проверку без выразительности (обобщённые
`out?`-параметры zero-allocation математики на JSDoc не выражаются), а Flow мёртв.
`target: ES2020` без Babel — потому что любой браузер с WebGL2 уже понимает ES2020;
транспиляция вниз только раздула бы бандл.

### 2.2 Three.js, а не Babylon.js / PlayCanvas / чистый WebGL

Нужен **бэкенд**, а не второй движок. Задача — Unity-подобный API сверху; всё, что
альтернатива приносит от себя, придётся либо обходить, либо прятать.

- **Babylon.js** несёт свой слой сцен, свою GUI-подсистему, инспектор, свою систему
  компонентов. Это прямое дублирование того, что здесь пишется (`Canvas` UI, `GameObject`,
  `Component`) — конфликт абстракций на каждом шагу, и бандл заметно тяжелее.
- **PlayCanvas** ориентирован на свой облачный редактор; без него теряется половина
  смысла, а с ним появляется внешняя зависимость в обучающем контуре.
- **Чистый WebGL** означает написать заново загрузчики GLTF/DRACO/KTX2, теневые карты,
  пост-обработку. Это годы работы вне темы проекта.

Что даёт Three: минимальное ядро, tree-shakeable, самый большой в вебе набор загрузчиков
(GLTF, KTX2/Basis, DRACO), и — важное — отсутствие мнения о том, как устроена сцена. Плюс
`renderer.info` и `renderer.properties`, на которых стоит вся VRAM-диагностика.

**Измеренная цена:** Three не держит стабильный API между r-релизами. Именно поэтому
правило изоляции существует физически (конверсия только в приватных `_syncToThree` и
компании), а не декларативно, и поэтому возможен план перехода на WebGPU
(`design/render-adapter-plan.md`): кадровый шов уже обобщён — `RenderBackend` полностью
типизирован движком, и в тестах гоняется фейковый бэкенд.

### 2.3 `three` как peerDependency + доставка упакованным tarball

Не стилистика, а следствие измерения от **2026-09-05**. Редактор брал движок как
`file:../../WebEngineTS`, то есть директорию; симлинк позволял бандлеру разрешить
собственный `node_modules/three` движка рядом с копией приложения — **грузились две
инстанции THREE**, и проверки вида `instanceof THREE.Mesh` (их в рендеринге много,
например `Renderer._syncMaterialToThree`) начинали врать.

`npm pack` копирует реальную опубликованную форму пакета: three внешний, разрешается из
`node_modules` потребителя. Ровно одна инстанция.

Чем лучше альтернатив: `npm link` и npm workspaces дают «живую» связь, но именно ту
симлинк-семантику, которая сломалась; плюс симлинки не переживают Docker build context
у `virtual-lab`. `npm run release:local` закрывает удобство иначе — штампует временную
уникальную версию (`0.1.0-local.<timestamp>`) только на время `npm pack`, чтобы `npm
install` физически не мог переиспользовать старую сборку из кеша, и сразу возвращает
committed `package.json` на место.

### 2.4 Rollup, а не Vite / webpack / esbuild / tsup

Здесь собирается **библиотека с матрицей целей**, а не приложение: ESM, CJS, standalone
со вбандленным three, и один плоский `.d.ts`. Rollup единственный даёт все четыре
напрямую и при этом плоский, читаемый выход без рантайм-обёрток.

- **Vite** — инструмент разработки приложений; его library mode — это всё равно Rollup,
  только с меньшим контролем над многовыходной конфигурацией.
- **webpack** добавляет свой рантайм-скаффолдинг в бандл, который затем читается
  сценарными скриптами через import map.
- **esbuild/tsup** быстрее, но декларации всё равно собирают сторонними средствами
  (api-extractor или тот же `rollup-plugin-dts`), а `stamp-build-info` — это
  transform-плагин, которому нужен именно rollup-овый хук.

### 2.5 Standalone-бандл + `<script type="importmap">`

Сценарий — это ZIP со скриптами, которые исполняются из **Blob URL**. Им нужно уметь
написать `from "WebEngineTS"` без всякого бандлера на стороне хоста. Import map + один
standalone-файл решают это ровно, и при этом *все* сценарии на странице разделяют одну
инстанцию движка и одну — THREE.

Чем лучше альтернатив: собирать движок внутрь каждого сценария — это N копий, никакой
дедупликации и снова несколько THREE; глобальная `window.WebEngine` — это отказ от ESM,
от tree-shaking и от типизированных импортов в сценариях.

**Цена платится в CSP.** `script-src blob:` обязателен, иначе не запускается ни один
сценарий, а import map требует именно `nonce` (Chromium игнорирует CSP-хеши для import
map) — nginx штампует `$request_id` в тег через `sub_filter` и тем же значением в заголовок.
Всё это задокументировано в `nginx/csp.conf`, а `e2e/tests/csp.spec.ts` следит за тем,
чтобы новая `location` не уронила заголовки молча.

### 2.6 `cannon-es`, а не Rapier / ammo.js

Оба конкурента — WebAssembly. В этом проекте wasm стоит дороже, чем кажется: CSP уже
пришлось затягивать под Blob-скрипты, и измерено, что basis-транскодер KTX2 требует
`'unsafe-eval'` (одного `'wasm-unsafe-eval'` не хватает — Emscripten-глюй исполняет
строку). Тащить wasm ещё и в физику значит либо открывать `unsafe-eval` ради физики, либо
воевать с ним второй раз.

`cannon-es` — чистый TypeScript/ESM: никакого дополнительного фетча, отлаживается в
обычном стеке, легко ложится на engine-типы (`Vector3`, `Quaternion`) без маршалинга
через линейную память.

**Честная цена:** Rapier точнее и быстрее на больших сценах. Для обучающих сцен —
солнечная система, молекулы, лабораторные стенды — точность solver'а не является узким
местом; узкое место измерено и лежит в draw calls и VRAM, чем и заняты P1.4/P1.5.

### 2.7 JSZip и почему при этом существует streaming-путь

ZIP распаковывается **в браузере**: сервер не разбирает контент, а значит его не надо
доверять серверу и не надо держать парсер форматов на бэкенде. nginx отдаёт байты, Express
вообще не стримит содержимое архивов.

Ограничение прямое и известное: монолитный ZIP целиком лежит в памяти. Это блокирует LOD-
стриминг, прогрессивную первую отрисовку, предзагрузку и дедупликацию между сценариями —
поэтому рядом живёт манифест-путь с адресуемыми по содержимому ассетами
(`design/asset-streaming-proposal.md`). ZIP-путь остаётся: он проще и для маленького
сценария быстрее.

### 2.8 `reflect-metadata` + legacy-декораторы для `@Serializable`

Unity-подобная сериализация требует знать типы полей в рантайме. Legacy-декораторы
(`experimentalDecorators: true`) выбраны, а не декораторы стадии 3, потому что только они
дают `emitDecoratorMetadata`-совместимое поведение с `reflect-metadata` и предсказуемо
работают в esbuild-based тулчейнах потребителей (Angular 19/21 собираются `@angular/build`).

Чем лучше альтернатив: кодогенерация потребовала бы собственного шага сборки у каждого
потребителя; ручные схемы пришлось бы синхронизировать с полями руками — а именно на этом
и споткнулся первый заход в сериализацию (`design/unity-parity-plan.md` описывает состояние,
которое уже устарело: сейчас `@Serializable` стоит на ~40 файлах).

### 2.9 UI на Canvas 2D, а не на three-меша́х и не на DOM

`Canvas` UI рисуется в **отдельный `<canvas>`** через 2D-контекст, размером в device pixel
ratio, с одним трансформом на перерисовку.

- **three-mesh-ui / спрайты в 3D-сцене** — это draw calls на каждый элемент интерфейса и
  заведомо хуже качество текста; ровно то, что P1 пытается сокращать.
- **DOM-оверлей** ломается там, где интерфейс должен жить внутри композиции канваса:
  fullscreen, pointer capture, единое hit-тестирование со сценой, единое масштабирование.

2D-контекст даёт резкий текст, бесплатное сглаживание, и — ключевое — hit-test в той же
системе координат, в которой рисуется. Отсюда же осознанный **Y-down** (top-left origin):
и 2D-контекст, и DOM-события уже Y-down, так что из каждого draw и каждого hit-test
убирается по одному флипу. Расплата — расхождение с Unity по знаку Y, и поэтому каждая
новая UI-возможность обязана объявить свою конвенцию в JSDoc.

`repaintMode: OnDemand` по умолчанию: канвас хеширует трансформ, локальный rect и
`_visualHash()` каждого графика и пропускает перерисовку, если ничего не изменилось.
Компонент, не переопределивший `_visualHash()`, возвращает `NaN` и считается всегда
изменённым — отказ от оптимизации безопасен по умолчанию.

### 2.10 Vitest, а не Jest

Тесты импортируют **исходники** через ту же резолюцию, что и сборка (`.ts`-расширения в
спецификаторах, `moduleResolution: bundler`). Jest потребовал бы ts-jest или babel-мост и
свою параллельную картину модулей — то есть тесты проверяли бы не тот код, который
собирается.

123 спека тут не метрика, а закрепление конвенций, которые иначе пришлось бы выводить
заново: намотка примитивов (`PrimitiveWinding`), цветовые пространства текстур
(`TextureColorSpace`), системы координат (`CoordinateSpaces`), область действия `maxSize`
(`MaxSizeScope`), сторона установки хука (`InstantiateGameObject`).

### 2.11 Playwright для e2e, а не Selenium / Cypress

То, что здесь нужно проверить, jsdom не умеет по определению: работает ли CSP с nonce на
import map, исполняются ли Blob-скрипты, поднимается ли WebGL-контекст, отдаёт ли nginx
архив. Playwright гоняет настоящий Chromium поверх **собранного стека** (есть
`docker-compose.test.yml` и `global-setup.ts`). Selenium — тяжелее и без встроенного
ожидания; Cypress исторически хуже с несколькими контекстами и файловыми загрузками.

### 2.12 Angular для платформы и редактора, а не React

Оба фронтенда — долгоживущие приложения с формами, роутингом, DI и большим количеством
панелей; редактор — это инструментальный UI, где структурность Angular (DI, типизированные
формы, модульность) выигрывает у свободы React по мере роста. Плюс LTS-цикл: для
университетского контура предсказуемость обновлений важнее скорости итераций.

**Честная проблема:** версии разъехались — редактор на Angular 19.1, платформа на 21.2.
Движок это переживает (он не зависит ни от одного из них), но редактор стоит подтянуть,
иначе `@angular/build` и TS-требования начнут расходиться настолько, что общий tarball
станет неудобно тестировать в обоих сразу.

### 2.13 Express + `pg`, а не Nest / Prisma / Mongo

Бэкенд у платформы намеренно тонкий: каталог, загрузка архивов, health. Шесть
зависимостей, `USER node`, `--omit=dev`. Nest принёс бы DI-фреймворк и декораторы ради
трёх десятков ручек; Prisma — ещё один шаг генерации и свой рантайм ради SQL, который
целиком укладывается в `init.sql` плюс `migrations`.

PostgreSQL, а не Mongo, потому что данные реляционные по природе (каталог ↔ сценарии ↔
версии архивов) и потому что content-addressed метаданные архивов выигрывают от
ограничений целостности и транзакций. Mongo здесь не даёт ничего, а отнимает джойны.

### 2.14 nginx отдаёт байты, Node — только API

Раздача архивов и ассетов идёт с volume, смонтированного в nginx **read-only**; Express
никогда не стримит их содержимое. Range-запросы, кеширование и sendfile — на C, а не на
event loop. Хешированные ассеты — `immutable`, а `index.html` — `no-cache`, иначе устаревший
SPA продолжает разговаривать с новым API.

### 2.15 Docker Compose, а не Kubernetes

Развёртывание — один хост в университетском контуре. Compose даёт всё, что реально нужно:
healthcheck'и, зависимости запуска (`condition: service_healthy`), именованные volume'ы,
лимиты CPU/памяти. k8s добавил бы control plane и эксплуатационную сложность без единого
выигранного свойства на этом масштабе.

### 2.16 KTX2/Basis — опционально и выключено по умолчанию

Транскодинг в BC7/ASTC/ETC2 — главный рычаг по VRAM, и движок его умеет
(`_TextureMemory.ts`, `MemoryReport.renderer.textureFormats`). Но транскодер требует
`'unsafe-eval'`, а в каталоге сегодня нет ни одного `.ktx2`. Поэтому `'unsafe-eval'` в CSP
**отсутствует сознательно**: принятие KTX2 означает пересмотр этой строки осознанно, а не
обнаружение проблемы в рантайме. Сам транскодер движок не поставляет — он не его.

## 3. Слабые места стека — честно

| Проблема | Природа | Что с ней делают |
|---|---|---|
| Three.js ломает API между r-релизами | внешняя | Изоляция физическая, а не декларативная; `RenderBackend` уже обобщён — `design/render-adapter-plan.md` |
| Ресурсы и граф сцены всё ещё типизированы Three (`Texture`/`Mesh`/`Material`, `Transform._object3D`; ~130 использований в 39 из 160 файлов) | внутренняя | Стадийный план: на каждой стадии остаётся ровно один путь до GPU |
| Одна инстанция THREE держится на дисциплине доставки | внутренняя | Только `.tgz`, никогда директория; `release:local` — единственный путь |
| Монолитный ZIP целиком в памяти | архитектурная | Манифест-путь параллельно, ZIP остаётся |
| `cannon-es` слабее Rapier на больших сценах | компромисс | Осознан: узкое место измерено и не в физике |
| Angular 19 против 21 между потребителями | сопровождение | Подтянуть редактор |
| WebGPU не поддержан | не сделано | P1.6, разблокирован после P2.8 |
| Готовность к интегрированной графике не проверена на железе | не сделано | Харнесс готов (`?gpu=`), нужен Intel UHD/Iris Xe и телефон |

## 4. Чего в стеке нет намеренно

- **Babel и полифилы** — `target: ES2020`; браузер с WebGL2 уже всё это умеет.
- **Runtime-валидатор схем (zod и подобные)** — сериализация идёт через декораторы и
  метаданные; второй источник истины о форме данных не нужен.
- **Второй профилировщик** — `MemoryProfiler`, `Profiler` и `Benchmark` — это API движка,
  и больше ни один слой не имеет права отрастить свой. Харнесс, который их гоняет, живёт
  в `WebEngineTS-Benchmarks`; контент сценария не имеет права содержать бенчмарк или
  тумблеры оптимизаций — харнесс управляет ими снаружи через URL-параметры.
- **Зависимость движка от любого потребителя** — поток строго односторонний:
  движок → tarball/standalone → потребители.
